# Phase 9: the AI assistant (9.0 foundations + 9.1 read-only chat)

**Status:** built on branch `phase-9-ai-assistant`. **Not merged, not deployed, no key set, switched OFF.** Only 9.0 and 9.1 are built.

## What it is, and what it is not
A chat inside Elite OS (left bar: **Assistant**; a link under the Inbox caption on phones). It looks things up and explains them: find customers, read quotes, appointments and projects, and understand the customer, quote or project you had open when you pressed Assistant.

**It cannot change or send anything.** No quote edits, no bookings, no WhatsApp replies, no automatic replies to customers, no voice. Those are later phases (below) and each needs its own approval.

## How it works
```
browser (Assistant screen) --aiChat--> Cloud Function --> model wrapper --> Anthropic API
                                           |  ^
                                           v  |  read-only tools (9) -> Firestore
                                  aiSettings / aiUsage / aiRate / aiLog
```
* **One question** = the function checks who you are (same staff allow-list as everything else), the on/off switch, the speed limit and the budget, then runs a short loop (at most 6 steps, at most 4 lookups per step): the model asks for a lookup, the function runs it, the model answers.
* **Stateless:** the browser sends the last 12 plain-text turns; the conversation is kept only in that browser tab (`sessionStorage`, cleared on sign-out). The server stores no conversation. Errors and lookup details never go back to the model.
* **The open customer/quote/project** is sent as ids only. The server reads the names itself, so a screen cannot feed the model made-up facts.
* **Model-independent:** Elite OS talks to a tiny interface (`complete({model, system, messages, tools})`). `anthropicModel()` in `functions/lib/ai.js` turns it into the Anthropic API (one `fetch`, no SDK, prompt caching on, retries on busy/failing servers, a time limit). Another provider is another adapter; nothing else changes. **Models:** two, chosen by name on the screen: **Haiku** (`claude-haiku-5-5`, the default for everything) and **Sonnet** (`claude-sonnet-5-5`). The IDs live on the server only; the screen can send nothing but "haiku" or "sonnet" (anything else is refused). One model answers one question, start to finish: nothing escalates by itself. **"Retry with Sonnet"** under the last Haiku answer re-asks the same question, with the same earlier conversation, once, with Sonnet; it is a second request and counts against the same limits. The default can be changed with `aiSettings/current.defaultModel` ("haiku" or "sonnet").

### The ten tools (all read-only, strict input checks, small capped answers)
`search_customers`, `get_customer`, `get_conversation` (≤15 messages, each ≤300 characters), `list_quotes`, `get_quote`, `list_appointments`, `list_projects`, `get_project`, `pipeline_summary`. They use the same rules as the screens (e.g. the project status/"waiting to order" logic is checked against `public/project-model.js` for all 64 combinations). **The assistant never does maths:** prices are quoted exactly as stored; quotes are only ever calculated by the quote engine.

### Customer summaries: one format, built by code
Asked to summarise a customer, Haiku and Sonnet used to answer differently. The cause was both: the lookup left gaps (no Eircode field, appointments newest-first with past and cancelled ones mixed in, no "latest quote", no test-record hint), so each model filled them in its own way, and the answer format was free. Now the **server builds the summary** (`functions/lib/aiSummary.js`) from the records by fixed rules, in this order:
```
**Customer Name**
- Budget: €XX,XXX–€XX,XXX      (a clear free-text budget is reshaped; anything unclear is shown "as recorded"; none = not recorded)
- Location: Town
- Eircode: XXX XXXX            (from the saved address, else the notes; two different codes = not recorded)
- Latest quote: Quote number — Status   (the newest quote; "Sent (expired)" once its valid-until date has passed; none yet)
- Next appointment: Date, time (the next one that is not cancelled; none scheduled)
- Notes: only relevant information     (left out when there is none: project type, requirements, a short project status; not the lead-form boilerplate, address, Eircode or budget)
⚠ Possible test record: ...    (only when the name, email, phone, notes or quote number look like test data)
```
* The model's only job is to call `customer_summary`; its reply is the tool's text, so Haiku and Sonnet are identical by construction (a model's own wording is discarded). That also saves tokens: **no second model call** is made to restate it.
* **"Summarise this customer" with a customer open** (plain whole-message requests only: "summary", "overview", "summarise this customer", "tell me about her"…) needs **no model at all**: answered instantly, free, chip "No AI used". Anything more specific goes to the model as usual.
* Every other answer stays free-form, with the same short style rules for both models (answer first, no lead-in, "not recorded" for missing facts, one short ⚠ line for suspected test data). `get_customer` (for specific questions) now also returns the budget, Eircode, latest quote, next appointment and test hints, so no model has to dig for them.
* The summary never invents: a missing fact is labelled, free-text notes are shown as recorded (an instruction inside a note is just text on the screen).
Examples (from the test data): a full record, a sparse record (every missing field labelled), a test record (⚠ line) are in `functions/test/ai.test.js` ("EXAMPLES").

## Phase 9.2a: AI actions with approval (customer notes, project updates)
**Branch `phase-9-2a-actions`: not merged, not deployed.** The assistant can PREPARE a change; only a person can APPLY it.
1. **Propose.** Asked for a change ("note: call after 5pm", "tick doors ordered and set installation for 20 Nov"), the model calls `propose_customer_note` or `propose_project_update`. Code checks the request with the same limits as the screens, builds the **exact before/after preview**, and stores one `aiProposals/{id}` record. Nothing else is written. The model supplies only ids and the wording you asked for. The reply is a fixed sentence (no second model call), the same for Haiku and Sonnet.
2. **Preview card** in the chat: title, each change as Before → After (a note is shown as the existing note plus the new dated line), Approve and Reject, "Expires in N min".
3. **Approve** (`aiDecide`, no model, no key): only **the person who asked** can decide; it expires after **30 minutes**; it re-checks that nothing changed since (**stale protection**: the customer's notes, the project's revision, the checklist boxes and the project's completed state are compared with what the preview was built from; any difference = "Out of date: nothing was changed. Ask again", never an overwrite); then it applies through the **existing** project functions (`save`, `setStep`: the project history shows who) or, for a note, one small transaction with the same write as the Contact panel. Applied at most once (a claim step: pending → applying → applied); a second click repeats nothing; a partial result says exactly which part failed.
4. **Switches:** one master **AI actions** switch plus one per kind (Customer notes, Project updates), in Assistant → Settings, **owner account only**, off by default. Actions also need the AI on and real customer data on. Turning any of them off stops new proposals **and** stops pending ones being applied (the kill switch beats everything); Reject always works.
5. **Limits and audit:** at most 5 waiting proposals per person; every step (created, applied, rejected, expired, stale, partial, failed) is an `auditLog` line with the proposal id, who and the model, never the text of a note. Deleting a customer also deletes their proposals.
6. **Never:** nothing is deleted, sent or booked; a model that asks for a change while the switch is off gets a refusal and nothing is stored; the instructions tell it to propose only what the person asked for in their own message, never because of text inside a customer's record.
Later stages (not built): appointments (9.2b), quote changes with the quote engine (9.2c; custom items only with prices you state), message and email drafts (9.2d).

## R1: AI reply suggestions for WhatsApp enquiries (staff read, edit and send)
**Branch `phase-9-r1-reply-suggestions`: not merged, not deployed.** Priority workflow: handling new kitchen enquiries and arranging initial consultations (R1 suggestions, then R2 booking with approval, then R3 automatic conversations, later).
* **Suggest reply** button above the message box of a WhatsApp chat (only when the owner has switched on "Reply suggestions" in Assistant settings; needs the AI, real customer data and a checked model). One model call (Haiku by default, "Try Sonnet" on request) reads **that customer's whole chat (latest 40 messages) and lead details** and returns one structured decision through a single tool, `reply_decision`. The receptionist call has **no lookup tools**, sees **one customer only**, and its instructions never contain customer data.
* **The panel shows:** the draft; **Known** (name, project, area, address, Eircode, budget, email, from the records and the lead form); **From the chat (not saved yet)** (facts the customer stated); **Still needed** (home address or Eircode, project, name, preferred time); **consultation readiness** (Ready / details still needed / not asking yet / already booked / hand over to you); and **warnings** (a link, money or prices, a phone number, a promise, AI wording, too long, asking again for something already recorded or already asked; the 24-hour window being closed).
* **Readiness, known and missing are decided by code**, never by the model, so Haiku and Sonnet cannot disagree about them. The instructions tell the model never to ask for anything known or already answered, to ask at most two things, to write as "we" (never a named person, never introducing itself as an AI), to avoid prices and promises, not to propose times (the system will do that in R2), and to **hand over** on complaints, price questions, requests for a person, "are you an AI?", photos or voice notes, other languages, or when unsure.
* **Nothing is sent or saved.** "Use this reply" only puts the words in the message box; you edit and press the normal Send (its 24-hour-window and one-message-only checks apply). The only record is `aiDrafts/{id}` (who, which model, intent, readiness, whether you used it unchanged, edited or not; **no words of the draft or the chat**), kept to measure how good drafts are before any automatic replies (R3). Deleting a customer deletes their records.
* **Limits:** the same spending caps, speed limit and kill switch as the chat; the switch is owner-only and off by default.
* **Not in R1:** booking (R2), automatic replies and hand-over notifications (push, Inbox badge: R2/R3), email drafts.
* **Template for confirmations outside the 24-hour window:** `docs/WHATSAPP_APPOINTMENT_TEMPLATE.md` (to submit to Meta; needed for R2).

## R2a: the consultation-arrangement flow (fixed, decided by code)
**Branch `phase-9-r2a-scheduling`: not merged, not deployed.** The AI does **not** pick slots, book anything or promise availability. It collects the customer's preference and hands over to you; you confirm the exact appointment and book it through Elite OS as usual.
1. The customer is interested in a home consultation and has not said when suits: **"Would any day next week suit you for a home consultation?"**
2. If next week does not work: **"No problem. Would the following week suit you? Do you have any particular days or times that work best?"** (asked once).
3. As soon as there is any reasonable preference (a week, days, "any day", a time of day): **"Perfect, I'll pass that on to the team and we'll confirm a time shortly."**, the preference is recorded, the AI **stops asking about scheduling** and hands over.
4. **At most two scheduling questions.** If the customer still gives nothing: "No problem, I'll pass this on to the team and we'll be in touch to arrange a time." and a hand-over with "no preference given".
5. If the customer already said when they are free, **nothing is asked**: straight to step 3. If a consultation is already booked, or the customer is being handed over for another reason, the flow says nothing about scheduling.
* **The wording is written by code** (`functions/lib/aiSchedule.js`), never by the model, so it cannot promise or confirm anything; Haiku and Sonnet give identical lines. The model only reads the chat: it says whether the customer wants a consultation, extracts what they said about days and times, and may add a short greeting ("Hi Anna, thanks for getting in touch.") to **the first message of a conversation only** (checked: no question, no times, no promises). Anything else it writes about times is discarded.
* **What you see** in the Suggest reply panel: the scheduling step (asking about next week / the following week / preference received / no preference), a **"Preferred days and times"** box with the real dates ("Next week (Mon 19 Oct to Sun 25 Oct) · Tuesday 20 Oct, Wednesday 21 Oct · afternoons") and the customer's own words, the hand-over reason, and the usual Known / Still needed lists.
* **Memory:** you still send the messages. When you send a suggested scheduling message (used as it was or edited), the conversation records the step (`conversations/{phone}.consult`: stage, number of questions asked, the preference), so the next suggestion is the right one and nothing is asked twice. A discarded draft changes nothing; the flow never moves backwards. Messages you type yourself are recognised from the chat ("any day next week", "following week").
* **Data:** `aiDrafts` now also holds the preference the customer gave (their words and the summary), and `conversations/{phone}.consult` holds the flow state; both are erased with the customer.
* **Not in R2a:** the "consultation request" card and Inbox badge, the "Book appointment" shortcut, hand-over push notifications (R2b / R3). The WhatsApp confirmation template (`docs/WHATSAPP_APPOINTMENT_TEMPLATE.md`) is not needed for this flow because you confirm manually.

## R2b: consultation requests waiting for you (card, Inbox count, Book appointment)
**Branch `phase-9-r2b-consult-card`: not merged, not deployed.** Booking and confirming stay entirely with you. Nothing here books, sends or confirms anything.
* **When a customer is "waiting for you to book":** the consultation flow has handed them over (you sent the "I'll pass that on" or "no preference" message), `conversations/{phone}.consult.needsBooking` is true, they have **no appointment still to come**, and nobody pressed "Not needed". It clears by itself when an appointment exists.
* **The card** (top of that customer's chat): preferred days and times with the real dates and the customer's own words, project and place, the latest four messages (folded), and two buttons. It says plainly that nothing is booked or confirmed.
* **Inbox:** a **"Needs booking (N)" bar above the list** (works on a phone; it filters to the waiting customers whatever their stage), a "Needs booking" tag on their rows, and a second coloured badge on the Inbox item on wide screens. It is separate from the unread count.
* **Book appointment** opens the existing booking form with the customer selected, type Consultation, their location filled in, and the **date set to the first day they named** (the Monday of the week they named if they named only a week; never in the past; otherwise the form's normal default). You choose the time and press Book as usual.
* **Clash line in the booking form** (also when rescheduling): under the date and time, "Already booked that day: 10:00-11:00 Name" or, if the chosen time overlaps, "Clashes with: ...". Only a warning: it never stops you.
* **"Not needed"** (callable `aiDismissConsult`, staff only, no model, no secret) clears the waiting flag and keeps the record of what they asked for. A later hand-over raises it again.
* **Data:** `consult.needsBooking` / `dismissedAt` / `dismissedBy` and `consult.preference.firstDate` on the conversation; all erased with the customer. The screen reads upcoming appointments with one extra listener (a plain range on `start`, no new index); until it answers no card is shown.
* **A customer who already has a consultation booked and wants it changed** (handover reason "wants to change booking"): the line is written by code too. First time: "No problem, would any day next week suit you better?"; if they already said when, "Perfect, I'll pass that on to the team and we'll confirm a time shortly." with their preference shown; if we already asked, "No problem, I'll pass this on..." (never asked twice). It always hands over, leaves no consultation request card (you move the existing booking), and never mentions today or tomorrow.
* **Deploy:** backend = the `ai` stage (8 functions now; `aiDismissConsult` is new, nothing existing changes), then `live`.
* Tests: `functions/test/consult-model.test.js` (5, pure), the schedule and reply tests (R2b flag, "Not needed", input checks, no sending), `test-ui/assistant.e2e.js` (card, count, filter, Book appointment on the right customer and day, clash line, auto-clear, "Not needed", phone layout).

## R3: the automatic receptionist for new Meta leads
**Branch `phase-9-r3-receptionist`: not merged, not deployed.** The workflow it automates: (1) the customer fills in the Meta lead form, (2) Make sends our approved WhatsApp template (leadIntake, unchanged), (3) the customer replies, (4) the receptionist handles the reply and the conversation after it, without the owner opening Elite OS or switching anything on for the chat.
* **One master switch:** Assistant > Settings > **Automatic receptionist** (owner only), on top of the AI, real-customer-data and reply-suggestion switches. Off = it does nothing at all. Switching it on records the moment (`aiSettings.autoReplySince`).
* **Which chats (never retroactive):** only a **Meta lead** (`contacts.metaLead`) whose lead arrived after the switch went on AND whose conversation was created after it. Existing conversations, returning customers who submit a new form, and customers who are not Meta leads are never switched on. A chat is switched on once, by itself, the first time the lead replies; the decision is recorded so an explicit "off" from the owner is never undone. The owner can still switch any single chat on with its **Receptionist** button (used for testing with a test number).
* **Every minute** (`receptionistSweep`, scheduled, not callable from outside; the WhatsApp webhook and leadIntake are untouched) it looks at the chats where the customer wrote in the last 24 hours (the only ones that can be answered) and, for the switched-on ones, asks the same reply suggestion staff get, in a short **automatic mode** (it is told nobody reads the reply first; read the lead details and the whole chat; set intent honestly; hand over when unsure). The reply is sent only if every rule holds:
  * **Reads before answering:** lead form answers, the records and up to 40 messages (as for staff). It never repeats a question: the only question it can ask is the fixed consultation question; nothing the form or the chat already answered is asked.
  * **The words:** a one-sentence acknowledgement checked by code (no question, no number, nothing about days, times, prices, promises, links, AI) in front of the fixed question "Would any day next week suit you for a home consultation?"; then the fixed lines only: following week, "I'll pass that on", "no preference", the honest "automated assistant" line if asked, and the booking-change question. A model sentence that fails the check is dropped and only the fixed line goes out. A draft with any warning is not sent.
  * **Ordinary enquiries** (not only explicit consultation requests) count as interest in a consultation, so it guides every new lead toward one. Prices, discounts, delivery or fitting dates, process details, wardrobes, photos, voice notes, complaints, "talk to a person", anything unclear: **no reply, hand over, push**.
  * **Preferred days and times** are collected by the fixed flow (max two questions); on a preference it sends "I'll pass that on…", records it and **hands the chat to the owner** (the request card, Needs booking count and Book appointment of R2b), with a push.
  * **Never invents a price, promises availability, books, edits or cancels anything**; the owner books and confirms himself.
  * **Safe against duplicates and retries:** a webhook delivered twice stores one message; a claim is made before every send (as for staff sends); a per-chat lock (state re-read inside it) stops overlapping checks; a failed or unconfirmed send hands over and is never resent by itself; at most **6 automatic messages a customer a day**.
  * **WhatsApp rules and quiet hours:** only plain text inside the 24-hour window; **nothing between midnight and 7:00 Irish time** (it waits and answers after 7:00); only messages the customer sends after the chat was switched on, at least 45 seconds after the last one.
* **Push notifications:** a new kind `handover` ("A chat is waiting for you", no names or words) whenever a chat needs the owner: a consultation preference collected, a refusal to guess, a failed send or AI call, a booking change.
* **Taking over:** anything a person sends in the chat (apart from our welcome template) stops the automatic replies for good, until the owner presses Receptionist to restart that chat. Every chat has its own **Receptionist** button: on (automatic) / on / handed to you / off. Pausing an automatically switched-on chat keeps it off.
* **Labelled:** automatic messages show a "Receptionist" tag (`auto: true`). It does not introduce itself as an AI (the owner's choice, see above) and tells the truth when asked.
* **Deploy:** `ai` stage (adds `setReceptionist`), then the new `receptionist` stage (`receptionistSweep` + `pushReceipt`), then `live`. Stop it: the master switch (within a minute), a chat's button, or the AI kill switch.
* Tests: `functions/test/ai-receptionist-leads.test.js` (the owner's scenarios end to end: full journey, ordinary enquiries, prices and other things never guessed, only new Meta leads, master switch, per-chat control, manual take-over, duplicates and retries, WhatsApp rules and quiet hours, nothing booked), `ai-receptionist.test.js`, the schedule tests, `test-ui/assistant.e2e.js`.

## Safety rules (each one has a test)
| Rule | How |
|---|---|
| **Spending cap, enforced on the server** | Before every model call the function *reserves* the worst case of that call (input estimate + the maximum output) on the month and the day totals in one transaction; no room = no call, and the person is told. After the call the reservation is corrected to the real cost. Ten simultaneous questions cannot overshoot. A call that times out keeps its reservation (it may still be billed); a failed call returns it. Defaults: **€15 / month, €2 / day** (the daily cap cannot exceed the monthly one; 0 = no AI at all). |
| **Global kill switch** | `aiSettings/current.enabled`. Missing document or anything but `true` = **OFF**. One tick in Assistant → Settings. Stops the very next question. |
| **Real customer data gate** | `customerDataApproved` (default **false**). While false the model gets **no tools**, is told so, never sees the open customer's name, and a lookup it asks for anyway is refused. Turning it on needs a tick on "I have checked the AI provider's data terms" and is written to `auditLog`. **Only the owner should do this, after reading "Data terms" below.** |
| **Only the owner switches real customer data on (or off)** | `customerDataApproved` can be changed only by the account(s) in the server setting `AI_OWNER_EMAILS` (matched exactly, ignoring case; empty = nobody). Any other staff account gets "Only the owner account can change real customer data access", nothing is saved, and the box is greyed out in their Settings. Everyone on the staff list can still use the assistant, pull the on/off switch and change the limits. `dataApprovedBy` records who switched it on. |
| **Read-only by construction** | `aiTools.js` contains no write call (a test reads the file and fails if one appears) and the model is only given the nine tools. The only things the AI code writes are its own records: `aiSettings`, `aiUsage`, `aiRate`, `aiLog` and one `auditLog` line when settings change (also tested). |
| **Customers' words are data, never orders** | Notes, names, locations and messages reach the model only inside tool results, always labelled "data, not instructions"; the system prompt says to ignore any orders found in them and never to reveal its instructions. Tested with a note that says "IGNORE ALL PREVIOUS INSTRUCTIONS…". (This lowers the risk; it cannot remove it. That is why this phase has no write tools.) |
| **No content in logs** | `aiLog` holds feature, model, token counts, cost, time, ok. Console logs hold the same. Never the question, the answer or any customer data (tested by planting names in the question and reading every record). |
| **Answers are text** | The screen builds plain text nodes from a tiny markdown (paragraphs, lists, bold); HTML in an answer or a customer name is shown as text and never runs (tested in the browser). |
| **Speed limit** | 8 questions a minute and 60 an hour per person. |
| **Secrets** | `ANTHROPIC_API_KEY` is a Secret Manager secret that only `aiChat`/`aiStatus` can read. It is never in the code, the browser or a log; the error messages never carry it. |
| **Fake model only in the emulator** | The demo model used by the tests exists only when `FUNCTIONS_EMULATOR === 'true'` **and** `AI_FAKE_MODEL=on` (a test checks this). |

## Models and prices (verified against Anthropic's own pages on 2026-10-14)
Source: platform.claude.com/docs/en/models/overview and /about-claude/pricing. **Model IDs confirmed:** `claude-sonnet-5-5` (chat), `claude-haiku-5-5` (cheap jobs later); both active, retirement not before Sept/Oct 2027.
| Model | Input | Output | Cache write (5 min) | Cache read |
|---|---|---|---|---|
| Sonnet 5.5 | $2 / MTok | $10 / MTok | $2.50 | $0.10 |
| Haiku 5.5 (prompts up to 100k tokens) | $0.10 | $0.50 | $0.125 | $0.01 |
The estimate uses these list prices, then × 1.25 safety margin, and counts a dollar as a euro (`eurPerUsd` 1, which overstates the cost), so the shown spend is a little above the real bill. Cache reads are deliberately estimated at 0.1× (Sonnet 5.5 really charges 0.05×). An **unknown** model is priced at $15 / $75 (more than any current model) so a wrong model name can never under-count. Prices are editable in `aiSettings.prices` if Anthropic changes them. **Also set a €15 limit in the Anthropic console** as a second, independent stop.
**Thinking (found while verifying, and handled):** these models think before answering by default; that thinking is billed as output and counts towards `max_tokens`, and within a lookup turn the model's thinking blocks must be sent back unchanged or the API refuses. So: the adapter sends them back exactly as received (tested); Sonnet 5.5 is set to its lowest thinking setting (`between_tools`; it rejects "disabled") and Haiku 5.5 to "disabled", both at medium effort; `maxOutputTokens` is 2048 (thinking included); a question may not start a new model call after 100 s. A typical question costs a fraction of a cent to about a cent on these numbers.


### Checking the models against the provider before use
**Check models** (Assistant → Settings, free, no tokens) asks the provider's own Models API (`GET /v1/models/<id>`) whether each model ID exists, is active, supports the effort setting we send, and accepts the thinking setting we send (Haiku: "off" must be accepted; Sonnet: "thinking" must be supported). The answer is stored (`aiSettings/modelCheck`) and audited. **A model that has not passed, or whose ID has changed, is refused by the server.** The Models API does **not** return prices, so prices are checked against the price page (above) and, after the first real questions, against the cost shown in the Anthropic console usage page (deployment step 7).

## Data terms (checked 2026-10-13; **you must verify before you switch real customer data on**)
From Anthropic's own pages (`privacy.claude.com`, `platform.claude.com/docs/en/manage-claude/api-and-data-retention`; secondary reading, please confirm on your account):
* **Training:** commercial API inputs/outputs are **not used to train** models by default. Exceptions: feedback you choose to send, and content you explicitly opt in to share.
* **Retention:** by default API inputs/outputs are deleted from Anthropic's backend within **30 days**. Content flagged by their safety systems can be kept up to 2 years (classifier scores up to 7 years); legal holds apply.
* **Zero Data Retention (ZDR):** exists, but is **per organisation by agreement with Anthropic**, not automatic. Without it the 30-day rule applies.
* **Location (checked 2026-10-14):** the first-party Claude API offers **no EU processing or EU storage**. Inference is "global" (anywhere) by default; the only alternative is US-only ("us", +10% price), and workspace storage is US-only. So customer data sent to the assistant is processed outside the EU (a GDPR international transfer): check Anthropic's Data Processing Addendum and its transfer mechanism for your account, tell customers in your privacy notice, and decide whether that is acceptable. (Other routes with EU regions exist, e.g. through Amazon Bedrock or Google Cloud, but they are different accounts and not built.)
**Decision for you:** accept 30-day retention (no ZDR) or ask Anthropic for ZDR; then tick the box in Settings. Until then the assistant works only on general questions.

## Customer-facing AI (not built yet): disclosure policy
Decisions recorded (2026-10-13): the future WhatsApp receptionist (9.4/9.5) **will not introduce itself as an AI** and will sound natural, warm and professional on behalf of Elite Kitchens; it will **never pretend to be a named employee**; and it will **answer truthfully if asked** whether it is an AI. Before it is ever enabled for automatic customer conversations the disclosure rules must be checked and complied with.
**Flag (please read):** EU AI Act Article 50(1) requires people to be told they are talking to an AI system **unless that is obvious to a reasonably well-informed person from the context**. As I read the secondary sources, this obligation applies from **2 August 2026**, so it is already in force. A WhatsApp receptionist with no introduction and no disclosure may not satisfy it. Options when we reach 9.4: (a) a short, friendly one-line disclosure (the safe route, small effect on warmth), (b) legal advice that the context makes it "obvious", (c) a human always sends. I have not given legal advice and did not read the official text; **take this to a solicitor before 9.4.** Nothing in 9.0/9.1 talks to customers.
