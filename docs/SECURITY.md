# Security model and review (Phase 2)

## Who can do what
| Thing | Who | How it is enforced |
|---|---|---|
| Open the app | Google accounts in `ALLOWED_EMAILS` only | `claimAccess` (verified email + allowlist) sets the `staff` claim **with an expiry** (`staffUntil`, 12 hours); the app renews it every 30 minutes while the person is still allowed. A removed person loses access when the claim runs out (about an hour after their sign-in session ends at the latest); `node scripts/revoke-staff.js their@address` ends it at once (Phase 6.1 audit, finding 5) |
| Read customers/conversations/messages | Staff with an unexpired claim | Firestore rules (`staff == true` **and** `staffUntil` in the future; a claim without an expiry is refused); nobody can write from a browser |
| Every action (send, edit, mark read, media) | Staff | Each callable runs `assertStaff` (signed in + claim + still on the allowlist) |
| Receive WhatsApp events | Meta only | `X-Hub-Signature-256` HMAC with the app secret; verify token for the handshake; other phone numbers' events ignored |
| Customer photos/files | Staff, via 10-minute signed links | Storage rules deny ALL browser reads/writes under `media/`; `mediaUrl` checks staff + that the path belongs to that conversation |
| Uploads to send | Staff, own folder, create-only, <=100 MB | Storage rules; `sendMedia` re-validates type/size/path, checks the 24h window, then moves the file into private `media/` |
| Appointments (Phase 5) | Staff | Read through the same staff-only rules (no browser writes); book/reschedule/cancel/retry through callables that run `assertStaff` and hold no WhatsApp secrets |
| Write to the shared Google calendar (Phase 5) | Elite OS only, via `ek-calendar` | Keyless: the functions' runtime account gets 1-hour tokens for `ek-calendar` (Token Creator on that account only), `calendar.events` scope; `ek-calendar` has no project roles and no keys; the calendar is shared for editing with it alone, people get read-only |
| Run the calendar sweeper (Phase 5) | Cloud Scheduler only | `calendarSweep` is not public; `deploy-appointments.sh backend` verifies it (`docs/APPOINTMENTS.md`) |
| Reopen a closed WhatsApp conversation (Phase 6.1) | Staff | `reopenConversation` runs `assertStaff`, holds only the WhatsApp access token (not the app secret or verify token), claims the send before contacting Meta, allows one template per customer per 24 hours, and logs codes only (`docs/PHASE6_1_PLAN.md`) |
| Send a quote by WhatsApp or email (Phase 6.1) | Staff | `deliverQuote`, `retryQuoteDelivery`, `resolveQuoteDelivery`, `cancelQuoteSend`, `markQuoteSent` and `quoteChannels` all run `assertStaff`. The recipient is never taken from the browser: the WhatsApp number is the quote's own, the email address is the customer's saved one (a changed address stops the send). Only the two that send hold the WhatsApp token. Every delivery is claimed (compare-and-set) before the provider is contacted, so a double click, a refresh or two staff cannot send twice; an unsure result is never retried automatically |
| Send a quote in the approved WhatsApp template when the 24-hour window is closed (Phase 6.1 M7) | Staff | The same callables and checks as any quote send; the server (never the browser) decides the route at send time. The template name and language are plain settings (`WHATSAPP_QUOTE_TEMPLATE_NAME`/`_LANG`, blank = route off), not secrets. The recipient is still the quote's own customer and the header PDF is the stored one (read back and checked against its SHA-256); the template's words are fixed by Meta, so no staff-typed text can reach the customer through it. A "window closed" refusal (131047) sent nothing, so it alone may be followed by the template; any other or unclear answer is never followed by a second message. Logs hold codes only |
| Send email as info@elitekitchens.ie (Phase 6.1) | Elite OS only, via `ek-mailer` | Keyless, like the calendar: the functions' runtime account asks IAM to sign a one-hour request for `ek-mailer` (Token Creator on that one account), which Google Workspace domain-wide delegation allows for the **`gmail.send` scope only** (send-only: it cannot read, list or delete mail). `ek-mailer` has no project roles and no keys; no secret exists in the code, the settings or chat. Email is off unless `MAIL_SEND=on` (kill switch) |
| The quote PDF that is sent (Phase 6.1) | Staff only | The exact bytes are stored privately under `quotes/` (never a public link); what is sent is read back and checked against its SHA-256 first. WhatsApp gets an upload of those bytes, email gets them as the attachment. The chat keeps its own private copy under `media/`, shown to staff by 10-minute signed links |
| One staff reply = one message (Phase 6.1 audit, finding 6; second audit 6 adds `startConversation`; third check 6: the screen keeps the request identity of an uncertain answer and needs a decision) | Staff | `sendReply`, `sendMedia` and `startConversation` claim the request under the conversation (`sendRequests/{requestId}`) before contacting Meta: the same request again sends nothing; a provider answer that cannot be confirmed is "not confirmed" and never resent by itself; once Meta has accepted the message nothing after it (the chat record, moving the file) can turn it into a failure. Logs hold codes only |
| Push notifications (Phase 8) | Staff | `registerPushDevice`, `unregisterPushDevice` and `sendTestPush` run `assertStaff`; a person only removes or tests their own devices. A push goes only to devices of people on `ALLOWED_EMAILS` who switched it on. The push holds opaque ids only (no name, number or text; tested). `pushReceipt` is public on purpose (a service worker has no sign-in): POST only, 1 KB, both ids must be known, the first report per kind wins, nothing is returned. Sending can never break or hold up the WhatsApp webhook or lead intake (2.5 s cap, errors swallowed; tested). Notification records are erased with the customer |
| Projects (Phase 7) | Staff | `createProject`, `saveProject`, `setProjectStep`, `completeProject`, `removeProject`, `attachProjectRender` and `projectRenderUrl` all run `assertStaff`; the project of an accepted quote is made by `acceptQuote` itself, in the quote's own transaction. Browsers can read `projects` (the staff-only read rule) and can never write one (tested). Every field is checked; notes are limited to 2,000 characters |
| The approved 3D render (Phase 7) | Staff only | The browser drops the file in its own `uploads/<uid>/` folder (create-only); `attachProjectRender` checks the real content (JPG, PNG, WebP or PDF by its first bytes, not by its name or declared type), the size (25 MB), and that the path is the caller's own, then moves it to `projects/<phone>/<project>/` (closed to browsers). It is shown through a 10-minute signed link, only after the stored size is checked against its record. Anything refused is deleted from the upload folder |
| The AI assistant (Phase 9.1) | Staff | `aiChat`, `aiStatus` and `setAiSettings` run `assertStaff`. **Read-only:** the model gets nine lookup tools and no write tool (a test fails if `aiTools.js` ever contains a write call). The spending cap (default EUR 15 a month, EUR 2 a day) is reserved in a transaction BEFORE each model call, so ten simultaneous questions cannot overshoot; the on/off switch defaults to OFF; real customer data reaches the model only after `customerDataApproved` is set (with an explicit confirmation, audited). `ANTHROPIC_API_KEY` is a Secret Manager secret read only by `aiChat`/`aiStatus`. Browsers cannot write `aiSettings`, `aiUsage`, `aiRate` or `aiLog`; none of them holds a question, an answer or customer data. Customers' own words are passed to the model only as labelled data. See `docs/AI.md`. |
| AI actions with approval (Phase 9.2a) | Staff, one person per proposal | The model can only create a proposal record (`aiProposals`); applying it is the separate `aiDecide` function (staff only, no model, no key), which only lets the person who asked decide, refuses expired or out-of-date proposals, applies at most once through the existing project functions or one note transaction, and writes an audit line (never the note text). The master AI-actions switch and the per-kind switches are changeable by the owner account only and are off by default; nothing is deleted, sent or booked. See `docs/AI.md`. |
| AI reply suggestions (Phase 9 R1) | Staff | `aiSuggestReply` and `aiDraftOutcome` run `assertStaff`. The suggestion reads one customer's records and chat, makes one model call whose only tool is the decision (no lookups, no actions), and writes only an `aiDrafts` record without any words; it sends nothing (staff send through the normal Send). The switch is owner-only, off by default, and needs the AI and real customer data on; spending caps, speed limit and kill switch apply. Erased with the customer. See `docs/AI.md`. |
| The stored quote PDF cannot be replaced (Phase 6.1 audit, finding 1; second audit 1) | Staff | Written create-only under a name that is private to the call that wrote it (random part + the SHA-256), so no call can delete a PDF another call committed; a request id is bound to one document; the PDF link re-checks size and SHA-256 before it is offered. Not covered: the PDF is made in the browser, so a modified browser of a signed-in staff member can upload a document that does not match the quote (accepted limitation, owner decision 2026-10-08; to be revisited with server-side PDF generation when the AI quote automation is built; see `docs/PHASE6_1_PLAN.md`, Audit) |
| "Do not contact" (Phase 10) | Staff set or clear it; the customer's own "stop messaging me" sets it | `setDoNotContact` runs `assertStaff`. EVERY way a message leaves Elite OS refuses a customer marked "do not contact" ON THE SERVER: `sendReply`, `sendMedia`, `startConversation`, `reopenConversation`, `deliverQuote`/`retryQuoteDelivery` (both channels), `sendQuote` ("mark as sent"), the Meta lead welcome and the automatic receptionist. Where a send is claimed in a transaction (`outbound.begin`, Reopen, the quote delivery claim, the welcome claim) the check is inside it. Tests: `functions/test/safety-dnc.test.js` |
| "Needs attention" and the health check (Phase 10) | Staff | `attentionAction` runs `assertStaff` and only closes a problem, clears a failed alert, closes a rejected lead (erasing its details) or saves the lead-warning hours. `healthSweep` (every 10 minutes) and `healthOnMessageWrite` (a message trigger) cannot be called from outside and hold no WhatsApp, Google or AI secret. Alerts carry no customer data: the push holds opaque ids, the email only the kind of problem (tested). Rejected leads (name, email, the number as typed) are staff-readable and erased once dealt with. Tests: `functions/test/safety-health.test.js` |
| Backups and recovery (Phase 10) | The project owner, from Cloud Shell | `scripts/setup-backups.sh` and `scripts/restore-docs.js` are not part of the app. A restore always goes into a NEW database; bringing records back never deletes anything and writes only what is missing unless told otherwise. Backups hold customer data, stay in the project, and expire after 14 days (`docs/BACKUPS.md`). |
| The Today tab (Phase 11) | Staff | `saveReminder` and `snoozeQuote` run `assertStaff`, hold no secret and send nothing. Reminders and quote follow-up notes are written only there (create-only ids from the request id; the quote's sent time is read by the server). The cards themselves are worked out in the browser from data staff can already read. Tests: `functions/test/today.test.js`, `functions/test/today-model.test.js` |

## Review results (2026-09-30)
- Every function has an auth guard (checked programmatically: webhook = HMAC, claimAccess = allowlist, all 7 others = assertStaff).
- No `innerHTML`/`eval`/`document.write` anywhere in the browser code; all customer-supplied text is inserted with `textContent`.
- No secrets in the repo or its git history (Meta token, app secret, private keys, API keys scanned). The "EAA..." pattern
  matches only the 1x1 test PNG embedded in the tests.
- Customer media is never public: verified by tests that the storage emulator refuses unauthenticated AND staff direct reads.
- `npm audit --omit=dev`: 0 high/critical, 9 moderate (transitive in firebase-admin 13 / firebase-functions 6).
  UPGRADED (chore/firebase-sdk-upgrade): firebase-admin 14.5.0 + firebase-functions 7.4.0 -> 2 moderate remain, both the same
  issue: uuid 9.0.1 pinned inside Google's @google-cloud/storage 8.2.0 (flaw needs a caller-supplied buffer to uuid v3/v5/v6;
  gaxios/we only use v4). Accepted residual; clears when Google updates that dependency. Not forced with an override because
  that would put untested code paths (signed URLs, resumable writes) into production.
- Hosting: no-cache + nosniff + frame-deny + referrer policy on our own pages (auth helper paths deliberately untouched).

## Known gaps / recommended next hardening
1. Rotate the Meta app secret and the webhook verify token (both were displayed during setup).
2. Firebase App Check for Storage/Functions (optional abuse protection; Firebase console suggests it).
3. Data retention / GDPR: there is no "delete a customer and their files" action yet, and no storage lifecycle rule.
   Customer photos are personal data: add an erase action and a retention policy before wide use.
4. Content-Security-Policy header (needs care with Google sign-in; test on the preview first).
5. Single allowlisted account today; add staff by editing `ALLOWED_EMAILS` and redeploying.
6. The quote PDF is generated in the browser (accepted by the owner, 2026-10-08): the server proves the stored bytes are the ones uploaded, not that they are the right document. Revisit with server-side PDF generation when the AI quote automation is built.
7. Staff access and the security rules must stay in step (second audit 7; third check 7: the live `claimAccess` is ASKED what it does, never judged by a deployment date; it answers one capability question without a sign-in and nothing else): rules that require the expiry refuse a claim without one, so an older `claimAccess` put back under them locks everyone out of the screen. `scripts/access-compat.sh` checks the live state and the deploy/rollback scripts refuse the dangerous order; `rules-back` is the safe way back.
